# django-rutoken-login

Беспарольная аутентификация для Django через USB-токены Рутокен.
Challenge/response поверх асимметричной криптографии (RSA/ECDSA +
SHA-256) — закрытый ключ никогда не покидает носитель, сервер видит
только подпись.

Проверен на реальном железе через
браузерное расширение «Адаптер Рутокен Плагин».

## Зачем это нужно

Большинство примеров интеграции с Рутокеном в сети — либо код от
вендора, который плохо ложится на Django-стек аутентификации, либо
внутренние наработки компаний, которые никто не выкладывает в опен-сорс.
Здесь — рабочий `AUTHENTICATION_BACKENDS` плюс весь фронтенд-код для
общения с плагином, без частей, специфичных для исходного проекта.

## Как это работает

```
Браузер                                   Django
   │                                         │
   │  POST /api/accounts/auth/challenge/     │
   │ ───────────────────────────────────────▶│  случайная строка, в Redis, TTL 60с
   │  { challenge, expires_in }               │
   │ ◀───────────────────────────────────────│
   │                                         │
   │  (плагин подписывает challenge           │
   │   закрытым ключом с носителя, нужен PIN) │
   │                                         │
   │  POST /api/accounts/auth/login/          │
   │  { certificate, signature, challenge }   │
   │ ───────────────────────────────────────▶│  1. challenge валиден и не использован? — забрать
   │                                         │  2. сертификат парсится как X.509 DER?
   │                                         │  3. thumbprint зарегистрирован, не отозван/просрочен?
   │                                         │  4. подпись верна для открытого ключа сертификата?
   │                                         │  5. django-axes не заблокировал этот thumbprint/IP?
   │  200 OK + cookie сессии                  │
   │  либо 400/401                           │
   │ ◀───────────────────────────────────────│
```

`CertificateAuthBackend` встраивается в обычный пайплайн
`authenticate()` Django и стоит *после* `axes.backends.AxesBackend` —
подсчёт неудачных попыток и блокировки достаются бесплатно, без
самописного rate-limiting.

Полный разбор криптографического контракта, схем эндпоинтов и
недокументированных нюансов формата данных от плагина —
[`docs/RUTOKEN_LOGIN.md`](docs/RUTOKEN_LOGIN.md).

## Стек

- Django 4.2+, DRF — под два API-эндпоинта
- `cryptography` — разбор X.509 и проверка подписи (RSA-PKCS1v15 и
  ECDSA, обе схемы на SHA-256)
- Redis (`django-redis`) — хранилище challenge, обязательно, а не
  опционально, как только в проде больше одного воркера gunicorn
- `django-axes` — блокировка после серии неудачных попыток
- Чистый JS на фронтенде (без фреймворков), общается с официальным
  загрузчиком плагина Рутокена

## Структура репозитория

```
apps/accounts/
├── models.py        User, TokenCertificate (привязка сертификата к пользователю)
├── backends.py       CertificateAuthBackend — только проверка подписи, никакой логики паролей
├── services.py       выдача/проверка challenge, разбор X.509
├── serializers.py    валидация входящих данных (DRF)
├── views.py           ChallengeView, CertificateLoginView, LoginPageView
└── urls.py

templates/accounts/login.html   вся форма входа + JS-оркестрация (поиск плагина → PIN → подпись → отправка)
static/vendor/                   официальный загрузчик плагина Рутокена (сторонний код — см. LICENSE)
docs/RUTOKEN_LOGIN.md            справочник по эндпоинтам, крипто-контракт, чек-лист интеграции
```

## Установка

```bash
pip install -r requirements.txt
```

1. Скопировать `apps/accounts/` в свой проект.
2. Скопировать `templates/accounts/login.html` и `static/vendor/`.
3. Перенести нужные куски из `example_settings_snippet.py` в свой
   `settings.py`. Отдельное внимание — `AUTH_USER_MODEL`, порядок
   бэкендов в `AUTHENTICATION_BACKENDS` и настройка Redis-кеша: именно
   здесь чаще всего ошибаются.
4. Перенести куски из `example_urls_snippet.py` в корневой `urls.py`.
5. `python manage.py makemigrations accounts && python manage.py migrate`
6. Зарегистрировать пользователя и сертификат:

```python
from apps.accounts.models import User, TokenCertificate
from django.utils import timezone
import datetime

user = User.objects.get(username="ivanov")
TokenCertificate.objects.create(
    user=user,
    serial_number="...",     # снять с реального сертификата —
    thumbprint="...",        # openssl x509 -noout -fingerprint -sha256 -serial -subject -issuer -dates
    subject_dn="...",
    issuer_dn="...",
    valid_from=timezone.now(),
    valid_to=timezone.now() + datetime.timedelta(days=365),
)
```

(Или проще — через `/admin/`, обе модели там зарегистрированы.)

7. Открыть `/login/` с подключённым носителем.

## API

| Эндпоинт | Доступ | Примечание |
|---|---|---|
| `POST /api/accounts/auth/challenge/` | анонимный, троттлинг 30/мин | Одноразовый challenge с TTL 60с, хранится в Redis. |
| `POST /api/accounts/auth/login/` | анонимный | `{certificate, signature, challenge}`, всё в base64. 400 при некорректном формате, 401 при неудачной аутентификации (намеренно без деталей — не палит причину отказа). |

Полные схемы запросов/ответов и формы ошибок — `docs/RUTOKEN_LOGIN.md`.

## Чего здесь сознательно нет

- **Самостоятельной регистрации сертификата пользователем.** Администратор
  привязывает `TokenCertificate` вручную (или через `/admin/`).
- **Проверки отзыва по CRL/OCSP.** Проверяется только локальный флаг
  `TokenCertificate.is_revoked`. Если нужна проверка отзыва в реальном
  времени у удостоверяющего центра — добавлять самостоятельно.
- **Никакого запасного входа по паролю.** Модуль намеренно
  однонаправленный. Если нужен break-glass для первичной настройки
  администратора — подключайте `ModelBackend` условно на своей
  стороне, не встраивайте это в сам модуль.

## Грабли, на которые реально потратили время при отладке

- **Redis не опционален.** Challenge пишет один процесс, читает другой
  (другой воркер gunicorn обрабатывает POST на вход). `LocMemCache`
  молча ломает это в любом многоворкерном деплое — на каждой попытке
  входа будет «challenge истёк», без единой подсказки, в чём дело.
- **Плагин Рутокена отдаёт всё как hex с двоеточиями, не base64** —
  серийные номера, идентификаторы ключей и, что важнее всего, саму
  подпись из `rawSign()`. Сериализатор бэкенда ожидает base64.
  Конвертация уже реализована в `login.html` (`hexToBase64()`), но
  если дорабатываете код и видите `400: "Подпись передана в
  некорректном формате"` — вот откуда это берётся.
- **`rawSign()` с `computeHash: false` хочет сам хеш тоже в виде
  hex-с-двоеточиями**, а не сплошной hex-строкой — нигде явно не
  задокументировано, подтверждено на форуме Рутокена (ссылка — в
  комментарии в коде). Не учтёте это — плагин ответит невнятным
  `{error: 'Could not execute command', message: 2}`.
- **`SESSION_COOKIE_SECURE=True` за обычным HTTP молча ломает вход.**
  Никакого диагностируемого сообщения об ошибке, ничего полезного в
  логах сервера — браузер просто не отправляет cookie обратно, и вы
  получаете ошибку CSRF, которая на самом деле вообще не про CSRF. Не
  включайте `True`, пока перед приложением нет настоящего TLS.
